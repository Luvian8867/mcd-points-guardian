# 麦当劳积分守门员 (mcd-points-guardian)

> 麦当劳积分按月过期。一句话问清还剩多少、能兑什么。

![演示：一句话盘点积分，剔除已下架商品，给出兑换方案](assets/demo.gif)

<sub>积分账户数值为演示数据。这段输出可以用 <code>python scripts/rank_redemptions.py --demo</code> 原样复现。</sub>

一个基于[麦当劳官方 MCP Server](https://github.com/M-China/mcd-mcp-server) 的 AI Skill。盘点即将过期的积分，剔除已下架商品，对同权益商品去重取最低积分价，告诉你怎么把积分花掉。

## 它解决什么问题

麦当劳积分按月过期，过期额度和可兑商品都能查到，但需要自己留意时间、自己比对哪些商品兑得划算。大多数人不会每月专门做这件事，于是积分就那么放着。这个 Skill 把它压缩成问一句话。

问一句话就够了：

```
我的麦当劳积分快过期了吗
```

输出（积分数值为演示数据）：

```
积分体检：可用 3280 分，本月将过期 400 分。快看看有哪些优惠券能兑换吧

| 商品                   | 积分 | 兑换截止   |
|------------------------|------|------------|
| 6.9元可乐麦炫酷        | 50   | 2026-12-30 |
| 6.9元香芋派/菠萝派任选 | 50   | 2026-12-30 |
| 10.9元指定小食任选     | 100  | 2026-12-30 |
| 16.9元麦辣可乐组合     | 500  | 2026-12-30 |
| 17.9元板烧可乐组合     | 500  | 2026-12-30 |
| 21.9元巨无霸可乐组合   | 800  | 2026-12-30 |
```

清单顺序本身就是推荐：前面几件能用掉快过期的积分，中间是略微多花一点的，最后是券面档位更高的。最多列 10 条。

## 安装

### 1. 申请 MCP Token

前往 [open.mcd.cn/mcp](https://open.mcd.cn/mcp)，登录后在控制台激活并复制 Token。

### 2. 配置 MCP Server

参照 `mcp-config.example.json`，把 Token 填入你的 MCP Client 配置。**Token 请通过环境变量注入，不要写进任何会提交到仓库的文件。**

```bash
export MCD_MCP_TOKEN="你的Token"
```

支持的 Client 包括 Kiro、Cursor、Cherry Studio、Trae、VSCode。配置方式见[官方文档](https://github.com/M-China/mcd-mcp-server#25-各平台接入教程)。

### 3. 安装 Skill

把 `SKILL.md` 放进你的 Client 的 skills 目录：

| Client | 路径 |
|---|---|
| Kiro | `.kiro/skills/mcd-points-guardian/SKILL.md` |
| Claude Code | `.claude/skills/mcd-points-guardian/SKILL.md` |

### 4. 验证

```
我的麦当劳积分快过期了吗
```

## 独立运行排序逻辑

清洗和排序逻辑可以脱离 AI 单独运行和测试：

```bash
python scripts/rank_redemptions.py --demo
```

自带样例数据和回归断言，零第三方依赖，只用 Python 标准库。跑通即说明清洗与排序规则未被改坏。

也可以喂真实响应：

```bash
python scripts/rank_redemptions.py --input products.json \
  --now "2026-09-20 17:32:49" --available 3280 --expiring 500 --expired 4150
```

另有 `scripts/make_demo_gif.py` 用于重新生成上方演示 GIF，它是唯一需要第三方库的脚本（`pip install pillow`），与核心逻辑无关，不影响 Skill 运行。

## 目标用户

有麦当劳会员账号、积分长期闲置的人。尤其是偶尔才打开 App、从不主动查积分的重度外卖用户 —— 这部分人的积分损失最严重。

## 用到的 MCP 能力

必调 `now-time-info`、`query-my-account`、`mall-points-products`；按需 `mall-product-detail`、`mall-create-order`、`delivery-query-addresses`。

兑换走 `mall-create-order` 一个工具，虚拟券与实物由入参 `spuCategory` 区分。实现时以 MCP Server 实际暴露的工具列表为准。详见 [MCP_INTEGRATION.md](MCP_INTEGRATION.md)。

---

以下几节是实现笔记，面向想了解内部逻辑或二次开发的人，使用这个 Skill 不需要读。

## 推荐分三档

用户的心智是「先把快过期的分用掉，多花一点也能接受，如果有更值的也想看看」。推荐按这个心智分三档依次排列：

| 档 | 条件 |
|---|---|
| 一 | 在过期额度内贪心装箱 |
| 二 | 略超过期额度，上限为额度 + min(额度×50%, 200) |
| 三 | 积分更高但券面档位更高，按券面金额降序 |

分档只决定顺序，不在清单里标注。顺序本身就是推荐，标出"用掉快过期积分""多付 100 分"这类理由反而增加阅读负担。

清单总条数上限 10，按档顺序填充。不限制各档件数，第一档最贴近用户目的，多占位是合理的。

券面金额从商品名解析（「21.9元巨无霸可乐组合」取 21.9）。要说清楚的是：这是**用券后的价格，不是原价**。接口不提供原价，所以本项目无法计算真实优惠额，只把它当消费档位的代理指标。任何地方都不会声称"帮你省了多少钱"。

## 四样刻意不展示的东西

**过滤统计。** "50 件里 19 件已下架"这类信息运行时输出里没有。用户没有全量兑换清单的概念，也不关心哪些商品被过滤掉了，只想知道自己的积分能兑什么。数据完整性自检仍然每次都跑，但降级为内部校验，只在算不平时才提示"结果可能不完整"。

**历史已过期积分。** 接口返回了 `expiredPoint`，用它做"你已经损失了多少"的对比很有冲击力，但那是无法挽回的损失，主动摆出来只会引发损失厌恶情绪，读起来像在指责用户没管好积分。默认不展示，用户主动问才回答（脚本对应 `--show-history`）。

**覆盖百分比、缺口差额这类算账口径。** "覆盖过期额度的 50%""还差 200 分，加兑某件即可覆盖"都是内部自检概念的泄漏。"本月将过期 400 分"本身已经带足紧迫感，后面接一句行动召唤就够了，再解释缺口只会让输出变长、读者分神。用户问起怎么用完，再单独回答。

**每件商品的推荐理由。** 三档只决定顺序，不标注原因。清单就三列：名称、积分、兑换截止。

## 四个别人容易漏掉的细节

**可兑换状态要按 `downTime` 判定，不能只看 `status`。** 一次实测拉取返回 50 件商品，`status` 均为 `2`，其中 19 件的 `downTime` 已早于当前时间。只按 `status` 筛选，结果里会混进已过兑换截止的商品。本 Skill 用服务端时间对 `downTime` 做二次过滤。

**同一权益存在不同积分价。** 比如"10.9元指定小食任选"同时有 100 分和 200 分两个 SKU。不做同名去重取优，用户就会为同一份权益多付一倍积分。

**`shopId` 决定兑换链路。** `shopId=2` 是券和实物，走 `mall-create-order`；`shopId=5` 是派对、体验营、品鉴会，不消耗积分（`point=0`、`price` 为现金价），必须走门店场次预约，混在积分方案里是错的。实测 50 件里有 26 件属于这类。

**积分字段都是字符串，且可能带小数。** `point` 返回的是 `"800"`、`"50"` 这样的字符串，过期积分字段还可能带小数。不显式转数字就直接排序时，`"100" < "50"` 会成立，推荐顺序静默错乱，不抛任何异常。这是本项目遇到的最隐蔽的坑，脚本里有对应的回归断言。

## 安全说明

兑换类 Tool 会真实扣减积分且不可撤销。本 Skill 强制要求用户明确确认后才执行兑换，且一次只兑换一件商品。任何情况下不自动下单。
